Graph exploration remains read-only; repository registration is the dashboard's bounded write action and runs the same initial scan as the CLI. Of the card's Neo4j rows, active queries is attempted live via `SHOW TRANSACTIONS` and queued transactions has no source on this build. The Database & memory card is backed by `dashboard/db_metrics.py`: a 15-second sampler (one hour in memory) reading heap, RAM, swap, CPU and GC from the JVM's own JMX beans, the configured page cache size from `dbms.listConfig`, and store size from a walk of `DEVGRAPH_NEO4J_DATA_DIR`; each group is independently live or labelled unavailable, and page cache hit ratio has no source on Community. The force-directed graph settle uses a Barnes-Hut quadtree for repulsion, and query highlighting can dim non-matching entities without rebuilding the canvas.

Git-history sync and the dashboard's git-status/log paths tolerate empty repos (no commits yet) and commits with no author/message. Removed dead code in `dashboard/routes.py` that would have raised `NameError`.

- Batch order and graph accuracy (#1). Within one `index_paths` batch (a full scan, or a watcher batch), cross-file edges do not depend on file order. See `docs/superpowers/specs/2026-10-08-graph-accuracy-design.md`.
  - Every file's nodes are written first. Then source-file edges, docs-note edges (`SUPERSEDES`/`DECIDED_BY`/`links`) and Markdown `MENTIONS` are resolved against the whole batch.
  - A node several files produce (a `Datastore`, `Endpoint` or `Container` written with a `source`, or a C++ `Class` stub) doesn't depend on write order either. It keeps each claiming file's properties in `claims` (JSON with sorted keys), and `sources` stays sorted. Its properties are those of the alphabetically first source, re-attributed when that file stops claiming it. This replaced last-writer-wins, so a full scan now gives the first file's properties, not the last one's.
  - A route's handler stub is its own file-less `Function`. It never claims a real `Function` of the same name, so the graph is the same whichever file is written first. A FastAPI or Flask `Endpoint` `IMPLEMENTS` the stub and the route file's own function of that name, never a same-named function in another file. A Django `Endpoint` (views imported from `views.py`) still `IMPLEMENTS` every real function of that name, until imports are resolved. A non-Python route's `Endpoint` and stub take the same shape: a handler of the route's file is pinned to it and its owner (a Spring or ASP.NET action's class), and a handler another file declares is pinned where a call to it would resolve (an ES import's files, a Go package's directory), recorded in `name_refs` so a batch adding it relinks it; an inline handler implements nothing. Their files' replace unclaims their Endpoint edges as a Python file's does (`engine.SERVICE_API_SUFFIXES`), and their Endpoints join the owning-service `CALLS` pass. A code file's Module records the shared nodes it claims (`shared_claims`, hidden), so its next write unclaims just those instead of reading every shared node of the repository, which made a full scan quadratic in a repository's routes. The record is read under the Module's lock, a delete reads every claim, and a full scan rebuilds every record from the shared nodes' `sources` before it prunes or writes, so a record that lost a claim heals. A route on a router whose mount its file doesn't show (an Express router another file mounts, a gin `*gin.RouterGroup` parameter) gets its file's own `Endpoint`, `GET ?/:id (routes/users.js)`, instead of merging every file's `GET /:id` into one. A C++ out-of-class method (`void Widget::draw() {}`) claims a file-less `Class` stub for its qualifier the same way: it never merges onto the header's `Class`, and it goes with the last file that defines a method of it.
  - Across batches, a batch re-indexes outside files that refer by name to a node it adds: docs notes whose `SUPERSEDES`/`DECIDED_BY`/`links` name it, route files with a handler stub of a new Function's name, and (until index format 7) same-directory, same-extension Java/Kotlin files naming a new class. Since format 7 no file is re-indexed as an importer of a changed one: every code edge is a function of its writer's text, its resolver configuration and whether its target exists.
  - Markdown that mentions an added name (when mentions are enabled) gains `MENTIONS` edges to just the added names, without a full re-index. A shared `Container`/`Datastore`/`Endpoint` (or C++ `Class` stub) counts as added when a batch file newly claims it, so one deleted with its last claim and claimed again links back. For a name that already exists, these files come from existing `MENTIONS` edges; only names new to the graph need a text scan. At most 25 files are relinked per batch; the rest wait for a rescan.
  - In `skip` mode, adding a second node with an already-mentioned name leaves the existing `MENTIONS` edges until the doc is re-indexed (which drops them) or rescanned.
  - Edge sources are pinned to their file; only targets stay bare-name. Same-named functions in two files no longer share call edges.
  - Built-in extracted edges carry a sorted `origins` list of the files that wrote them. Provider edges, git-history `MODIFIES` and PR `RESOLVES` edges have none. A file's re-index retracts only the edges it no longer writes. So a removed call, base class, import, compose service or Markdown mention goes on the next save. `origins` is hidden in the dashboard's edge inspector.
  - Each Module records the by-name edges its file wrote in `name_refs` (reserved, and hidden like `claims` by `describe_node` and the dashboard's node inspector). When a batch adds a node that an outside file's by-name edge named, that edge is re-written from `name_refs`, with no file read and no cap. Examples: an `IMPORTS` of a new module, a supertype in another directory, `CALLS` from outside the batch, a restored import target.

  - Python call resolution (#1, audit B7/B8; `docs/superpowers/specs/2026-10-10-python-call-resolution-design.md`). An import targets every candidate file under the importer's ancestor directories (`p.py`, `p/__init__.py`, and `P/n` for `from P import n`), then (since index format 16) each `src` directory holding Python files beside one in a Python project (a `pyproject.toml`, `setup.py` or `setup.cfg` beside it), so `tests/` and `scripts/` beside a `src/` layout reach the package, and the source roots a `pyproject.toml` at or above it declares (setuptools `package-dir`/`packages.find where`, Poetry `from`, Hatch wheel `packages`; resolver configuration, so a changed root re-indexes every Python file), so flat, `src/` and nested layouts resolve; only existing Modules link. A call resolves, first match wins, to a def in the file or an enclosing function, an imported name's module (and any file under its package, for re-exports), `self`/`cls`/`super()` methods in the class or its bases (an imported base's module, not followed further), a module attribute, or a receiver typed by a parameter annotation, a same-file pytest fixture or `x = X(...)`. Edges carry `confidence`: `resolved` (a file the caller names), `package` (under an imported package) or `name` (an untyped receiver, linked by name). A builtin type's method on an untyped receiver, a literal receiver, and a bare name nothing defines or imports link nothing. Every Python edge is a function of its writer's text and whether its target exists: `name_refs` record pinned and package targets, and the relink restores them, so Python files are no longer re-indexed as reverse dependents of a changed import target (nor, since index format 7, Java ones). Graph insights leave out `name` and `package` calls; `find_callers` returns each caller's best `confidence`, resolved first, and takes `resolved_only`. On DevGraph itself multi-target call edges fell from 26,028 to 3,791 and the PageRank top ten holds no test helper or builtin method name. - Watcher correctness (#1) shipped: a running agent keeps a repository's graph equal to a fresh `full_scan` through file renames, and folder moves, renames and deletes (top-level folders included), edits made while it was off, and git checkouts and pulls. File renames are a delete plus a create; directory events are walked or expanded to exact file paths by `remove_paths`; top-level folder changes reconcile the watches; batches, catch-ups, the schema rescan and dashboard registration share one lock per repository; every `last_indexed` stamp is the start of the work it covers; the agent catches up incrementally on start and after a git operation, and retries a failed batch from a held-back floor (the last good stamp). Every successful catch-up (start, resume, post-git, retry) of a repository with a `.git` folder is followed by the git-history sync in the same locked job, so a commit whose post-git job a stop or pause cancelled, or one made while the agent was off, is synced on the next start. Docs notes under `docs_path` record their repo-relative path as `source_file` (they used the bare filename, so every catch-up pruned and recreated them, a live delete left the note behind, and two notes with the same filename in different folders shared one key); on a graph written before this, the next catch-up or rescan deletes every note whose `source_file` is outside the docs path (an upgrade cleanup in `prune_stale_files`, like the bare-Module one; skipped when the docs path is the repository root, where a bare key can't be told from a root-level note) and writes the notes again under their repo-relative path, so none is duplicated or lost, mentions on or off, and a bare key that names a real root file (`README.md` for `docs/README.md`) goes too, with its edges. A catch-up counts a docs-routed file as known only when a note holds its key (its mentions `Document` holds the same key). Before a dead watchdog emitter is stopped again (unscheduled by the reconcile, or by the observer's stop), its closed Windows directory handle is forgotten: watchdog keeps the value and would close it a second time, by then perhaps another object's handle. The tray tooltip reads `DevGraph (catching up)` and the dashboard's Entities pill `Catching up…` while that runs. A `devgraph remove` while the agent watches the repository (it deletes the graph from another process, maybe under a running batch) no longer leaves nodes behind: when the agent's registry poll sees the repository gone, it stops its watcher, waits for the batch lock and deletes the repository's graph again (`RepoSync.on_removed`; skipped if the agent begins stopping before it has the lock); catch-ups, git-history syncs and schema rescans that get the lock after the removal write nothing, and an insights refresh never recreates the `Repository` node. `devgraph doctor` reports graph data of unregistered repo_ids, nodes without a `Repository` node included, and `devgraph prune` deletes it. `tests/watcher/test_watcher_live.py` checks each scenario against a fresh scan, properties included. See `docs/superpowers/specs/2026-10-07-watcher-correctness-design.md`. Still open, each fixed by `devgraph rescan`: a modified existing file whose events were dropped outside a git operation; a file changed while the agent was off whose timestamps all predate the last update by more than 5 s (a clock moved back, a skewed network share, a Windows tool that restores the mtime); a top-level folder left unwatched once its schedule retries are used up (until the next top-level change or restart); `devgraph add`/`rescan` in another process not serialised with the agent; macOS (FSEvents) unsupported as an agent platform; linked worktrees and submodules (a `.git` file) get no post-git catch-up or git-history sync, only the catch-up on start. The git-history sync writes Commit nodes, `MODIFIES` edges and recency in `UNWIND` chunks of 1,000 rows (one statement per chunk and per blamed file, not per row; audit 5 item 10) and yields the batch lock between chunks and blamed files, at most every 0.5 s (`WatcherManager.yield_batch_lock`), so live batches run during a long first sync; a catch-up let in by a yield asks the running sync to run again when it ends rather than syncing under it, and a stop ends the sync with HEAD unrecorded (its writes are idempotent). On a 733-commit clone of this repository a first sync went from 152-166 s (12,231 autocommit statements) to 18-20 s (414) and `--full`'s reconcile from 67-69 s to 15.4 s, the same graph either way (the recency of two same-named functions of one file, last write wins, varied between runs before as after); the agent logs `Reading the git history of <repo> for the first time (N commits); live updates go on between its writes` before it starts. Pause watching waits up to 3 s (`STOP_WAIT_S`) for a running batch, catch-up or git-history sync, so it can block the tray menu that long. Quitting the tray or headless agent (`devgraph/agent/shutdown.py`) is ordered and bounded to 5 s in total (`SHUTDOWN_WAIT_S`): the dashboard is told to exit, the schema-rescan and insights schedulers stop (a rescan still waiting on the batch lock skips its scan), then the watcher, each waiting for its running work against one deadline, and the graph engine close gets the time that remains. Open `/api/events` streams are ended first, and uvicorn's graceful shutdown is capped at 1 s, so an open dashboard tab does not use up the budget; each step's failure is logged and the rest still run. `GraphEngine.close` refuses new sessions (`EngineClosed`, a `ServiceUnavailable`, never retried) and waits for open ones, health checks included, so the driver is never closed under a running query. The indexer re-raises `EngineClosed` past its per-file and per-pass handlers, so a batch or catch-up cut by shutdown fails as a whole and stamps nothing (the next start's catch-up covers it); a dashboard registration cut that way is logged at INFO and redone by the next start; a query still running at the deadline, such as the first git-history sync of a large repository, is abandoned with one warning and the driver is left open under it until the process exits. Not fixed by a plain rescan: a Module deleted and restored (`rm a.py; git checkout -- a.py`) loses its recency and `MODIFIES` edges until `devgraph rescan --full`.

With Neo4j down a call used to retry for the driver's default 30 s (about 34 s in all) and then return the raw `ServiceUnavailable`; the MCP server's engine (`server.mcp_engine`, `GraphEngine(fail_fast=True, connection_timeout_s=2)`; unset elsewhere, so indexing and the agent keep the driver's retries) turns the driver's retries off (`max_transaction_retry_time=-1`: the driver retries while the elapsed time is not past it, and a coarse clock can read 0), retries a read once, 0.5 s later, when it failed once connected (a transient error, an expired session, a connection lost mid-query, however long it ran; never a transaction timeout), never when no connection could be had, and bounds getting a connection (opening, handshake, pool) at 2 s, so a call fails in about 2 s at most on every platform: at once against a closed port, 2 s against a port that never answers the handshake (what Windows' 2 s refusal looks like). `_with_neo4j_errors` turns `ServiceUnavailable`/`AuthError` from any built-in (project and global tools through `tool_plane._failure`, `describe_node` through its own `_read`) into `Neo4j isn't reachable at <uri>; start Neo4j (...)` or a refused-login ToolError. `server.main` probes Neo4j once (not retried) and, with it down, starts and serves anyway, logging that message, rather than exiting; it then runs `init_schema(wait=False)` once, thread-safe, before the first built-in call that finds Neo4j reachable (`_SchemaProvisioner`), so a fresh database gets its indexes without the agent. `blame_component` and `find_requirements_for` return `{count, results, truncated}` envelopes with `max_results` (default 15) instead of every row (up to 10,000 commits of 500-character messages), read through `_list_query` with the `LIST_ROW_LIMIT` notice; `explain_architecture` takes `max_results`, wraps `services_and_datastores` and `endpoints` in envelopes, leaves services no endpoint calls out of `endpoints`, and sanitises its strings. The name lookups of `find_callers`, `impact_analysis`, `find_related_files`, `trace_design_rationale`, `find_requirements_for` and `list_recent_changes` start from labels (`tools._named_nodes`: one branch per built-in label and per declared label the server passes, each seeking `(repo_id, name)`) instead of `MATCH (n {name})` or a CALLS type scan over the whole database (audit 4, item 6, MCP half; `tests/mcp/test_tool_plans_live.py` checks the plans for `AllNodesScan`/`RelationshipTypeScan`). With 100k Functions and 300k CALLS in one test repository, `find_callers`, `impact_analysis` and `find_related_files` went from about 145 ms to 5.5 ms and `trace_design_rationale` from 143 ms to 2.5 ms; `list_recent_changes` on an empty repository from 168 ms to 4.5 ms. The engine's provider scans and the dashboard counts followed (see the per-file re-index entry above).
- `list_endpoints` (MCP): a repository's `Endpoint`s, or every repository's with `cross_repo` (behind the same gate), as a capped `{count, results, truncated}` envelope ordered by name. Each result splits the name into `method` and `path`, with `mounted` false for a route under a prefix its file doesn't show (`GET ?/:id (routes/users.js)`, its own path), and gives its `framework`, the `files` routing it, its `handlers` (`{name, file, owner}` of the Functions it `IMPLEMENTS`; an unresolved one's file-less stub with file and owner null) and the compose `services` it `CALLS`. Filters: `method` (any HTTP method token in any case, `PROPFIND` too, or `*`), `path_prefix` (whole segments; an unmounted route never matches; a Django pattern, stored without a leading `/`, is listed and matched with one), `framework` and `service`. A method that is no token is an error, an unknown framework one naming the valid ones, an unknown service the not-found error with similar names.
- MCP answers say where (audit 6, item 5): `find_callers` rows carry the caller's `owner` and `start_line`, and `impact_analysis` (and `impact_analysis_for_diff`) dependents their `file` and `owner` (`file` is always present, null for a file-less node; `owner` and `start_line` are left out when the node has none); `find_callers`, `impact_analysis` and `find_related_files` take `owner`, or a member named with its declarations (`A.run`, `A::run`, tried when no node has the exact name; `tools._owned_target`), as `get_source` and `describe_node` do, and an owner without that member is an error. `get_source` raises the not-found ToolError with similar names for an unknown name, file or owner instead of an all-null answer, and reads an absolute `file` inside the repository as its repo-relative path (`_normalize_file` with the root).
- The dashboard's Cypher console is bounded (audit 4, item 8): `/api/cypher` passes a server-side transaction timeout and a row cap to `GraphEngine.run_cypher_graph`/`preview_cypher_graph` (Run 60 s and 50,000 rows, the read-only preview 5 s and 5,000; `routes._CONSOLE_*`/`_PREVIEW_*`). Past the cap `_graph_shaped` stops pulling, discards the rest (the query still runs to its end, within the timeout) and returns `truncated: true`, which the console shows as a notice; a timed-out query returns a `Timeout` error saying so instead of the driver's "retry your operation" text. The preview stays debounced (450 ms) and now runs one query at a time (`schedulePreview`): text typed while one is running waits for it, only the newest is sent, and the running one's reply is ignored; a queued preview is dropped when a Run or canvas refresh started after it was queued, so it can't supersede that reply. An uncapped result (a later canvas refresh) clears the row-cap notice, never an error shown since. `tests/dashboard/test_cypher_preview.py` (truncation of `UNWIND range(1, 1000000)`, the timeout message, the bounds per mode) and `tests/dashboard/cypher_preview_ui.js` check it.
- The agent's log rotates (audit 4): the tray and headless agents wrote `devgraph.log` through a plain `FileHandler`, one INFO line per live batch, so it grew without bound. Both now use `AgentLogHandler` (`devgraph/agent/log_file.py`), a `RotatingFileHandler` at 5 MB with three older files (`LOG_MAX_BYTES`, `LOG_BACKUP_COUNT` in `devgraph/config/settings.py`) whose rollover moves the current file aside to `devgraph.log.rolling` before shifting the backups (only up to the first free slot) and moving it to `.1`: when the first rename fails (Windows, another process holding the file) nothing has moved; when the second fails the file is moved back, or, if that is refused too, kept as `.rolling` and folded in as the newest backup at the next rollover, never overwritten (a `.rolling` left by a crash is moved back at start when the current file is missing). The stream is always reopened, appending, so records keep going to the current file, and a failed rollover is retried after 60 s. `devgraph logs` reads `devgraph.log.1` before the current file, so its tail survives a rollover, and skips a file a rollover renamed under it (`tests/agent/test_headless_logging.py`).
- Test-suite speed (audit 4, item 10): the full run (4,178 tests) took 35 min, about 30 of them in the Neo4j tests, at 22% CPU: the time is Neo4j round trips, not Python. The slowest are the accuracy fuzz seeds (58-81 s each; per-file write transactions at about 40 ms each, and the fresh full scans), the docs-provider fuzz (48 s), the watcher live tests and a path-pin test that sleeps out Neo4j's 10 s minimum replan interval on purpose. The provider-scan fix above was the cheap win: the fuzz seeds went to 52-73 s and the docs fuzz to 27 s. pytest-xdist is not adopted: `-n 4 --dist loadfile` took 25.5 min instead of 35 (the run is bound by one Neo4j and the longest files), and failed a wall-clock bound (`test_unmatched_report_stays_fast_with_many_relationships_and_edges`, 0.28 s against 0.2 s) under the parallel load; about 25 test files assert wall-clock bounds, and several share fixed repository ids across files (`test_repo_a` in four MCP files) or create and drop database-wide constraints, so a parallel CI would need those reworked first. A session-end sweep in `tests/conftest.py` deletes the test repositories (`zz-`, `zz_`, `_smoketest_`, `test_repo_`, `test-repo`, `dash_repo_` ids) unique to their creation (a run of 8+ hex characters, digits among them: a uuid slice or an epoch stamp) that this test process passed to Neo4j and that didn't exist when the session started, so it never touches a real repository, an older leftover, or a fixed id such as `test-repo` another session may be using; a run whose teardowns all ran leaves nothing for it.
- Autocommit writes can no longer fail silently: `GraphEngine`'s autocommit statements go through `_run`/`_run_records` (`devgraph/graph/engine.py`), which consume or buffer the result inside `_retry_transient`. The driver's results are lazy, so an execution error (a deadlock, a lock timeout, a constraint violation) used to surface in the next statement's retry, which re-ran the wrong statement, or in the session's close, which only logged a warning, so the indexer carried on as if the write had happened. Managed transactions (`execute_write`/`execute_read`) were already correct; `run_cypher`/`run_cypher_graph` read their whole result inside the session and are deliberately not retried.
- Audit 5, first-run batch. A stale `tray.pid` no longer adopts an unrelated process (item 1): the starter records the agent's pid with its start identity (Linux `/proc/<pid>/stat` start time plus boot id, Windows `GetProcessTimes` creation time, `ps -o lstart` elsewhere), and `lifecycle.read_tray_pid` returns a pid only while that process has the same identity and, where the command line can be read (not on Windows), runs `devgraph.agent.tray`; anything else (a file from before this, a reused pid) is removed as stale, so `tray status` says not running, `tray start` and MCP auto-start start a new agent, and `tray stop`/the last MCP holder never signal it. A record with no identity (pre-upgrade, or written when the start time couldn't be read, which logs a warning) is accepted when the process's command line runs the agent, or on Windows while the heartbeat is fresh, and is then rewritten with the identity, so `devgraph update` still stops the old agent. A stale record is deleted only if the file still holds exactly the record checked, so a starter's fresh record is never removed; `ps` runs with `LC_ALL=C` and `TZ=UTC0` so a macOS identity doesn't depend on the locale or time zone. The agent drops its own record on every exit path, the headless agent included. `devgraph doctor` names the first-run failures (item 7): a refused login (any `Neo.ClientError.Security.*`: a wrong password, too many failed attempts, expired credentials) gets `_neo4j_problem`'s settings-and-`.env` line instead of a raw driver error under "Not reachable" (and Podman stays informational, since Neo4j answered); a failing `podman ps` (exit 125 with the Podman machine stopped) shows podman's error and `podman machine start` (stated as the cause only when podman's error names the machine, otherwise offered as a likely one on Windows and macOS), not "container not found"; and a `devgraph-neo4j` container in any state but `running` fails, while Neo4j is down, with `podman start devgraph-neo4j`. Its container check matches the name exactly (`name=^devgraph-neo4j$`). First run waits for Neo4j (item 8): `graph.engine.wait_for_bolt` polls a bare driver's `verify_connectivity` (5 s connection timeout per try, no retries inside a try, so the wait ends within about 5 s of its deadline) until Bolt answers (a refused login counts; only `ServiceUnavailable`/`SessionExpired`/`TransientError` are waited out) or the deadline passes, and `devgraph doctor --wait SECONDS` runs it before its checks, printing progress every 10 s and how long it waited. A fresh container accepted TCP at once but answered Bolt after about 18 s, so `_bootstrap-core.ps1`'s TCP-connect loop and inline `init_schema` are replaced by `doctor --wait 90` (doctor creates the schema), and the Linux quickstart runs `doctor --wait 90` before `register`. `install.ps1` runs its body in `& { ... }` and stops with `return` and `$LASTEXITCODE` instead of `exit`, which under `irm | iex` closed the user's window; it was not run here (no PowerShell on the Linux host), only checked as text by `tests/scripts/test_first_run_scripts.py`. MCP registration drift (item 11): `mcp add` and `mcp doctor` read the `Command:` line of `claude mcp get devgraph` and compare it, symlinks unresolved, with this checkout's Python; a command that no longer exists fails both with `devgraph mcp add --replace` (new: `claude mcp remove -s user`, then add), and another existing checkout's is a warning with the same fix. Environments are compared by the interpreter's folder as written (`python` and `python3` in one `.venv` match; symlinks unresolved), a bare command is looked up on PATH, and a command that isn't a Python (`uv`, `uvx`, `pipx`, a console script) is left alone and never replaced. `--replace` removes the old entry first (Claude Code refuses a duplicate name) and adds it back if the new add fails. The VS Code entry's `cwd` is `${workspaceFolder}` (VS Code's MCP configuration documents predefined variables) instead of the DevGraph checkout; in a multi-root workspace or a window with no folder it names no single repository, and `DEVGRAPH_MCP_REPO` in the entry's `env` is the fallback (documented).
- Audit 6, robustness batch. The dashboard canvas no longer downloads a whole repository (item 2): its default node ceiling is `CANVAS_NODE_CAP` (1,500) when the scope is larger, so the state query always carries `WITH n LIMIT` until the user releases the slider at a maximum above the cap (reset by a repository or isolation change), and the console notice reads `Showing 1,500 of N nodes: narrow the view ...`. The canvas sends `canvas: true` to `/api/cypher`, which keeps only the properties it draws (`routes._CANVAS_NODE_PROPERTIES`), no relationship properties and no node values in rows. `reindexed` (and, while colouring by community, `insights_refreshed`) events are coalesced: one refresh per 1.5 s window, 15 s for a capped view, never two at once. Measured on a synthetic 2,061-file Python repository (24,282 nodes) through the real FastAPI app: the default canvas request went from 23.6 s, 412 MB and a 1.65 GB peak RSS (and truncated at 50,000 rows, 10,461 nodes) to 2.5 s, 4.5 MB and 225 MB (1,800 nodes, 1,500 matched plus their neighbours).
  - Graph insights no longer recompute after every save (item 7). `InsightsScheduler` (still a 30 s pass) refreshes a stale repository once its indexing has been quiet for 60 s (`_SETTLE_S`), or while edits go on once its insights are 10 minutes behind (`_MAX_LAG_S`), and never sooner than 5x the last run's duration after it (`_DURATION_FACTOR`). `refresh_insights` stores a fingerprint of the loaded graph by node identity (label, name, file, owner) and stored community, with its edges, as `Repository.insights_fingerprint`; the scheduler passes it back, and a graph that still matches (a comment or docstring edit, a body making the same calls) is only loaded: nothing is computed or written and no `insights_refreshed` is published. A re-created node that lost its scores changes the fingerprint. The dashboard's Recompute and `devgraph insights` always compute. Measured on the same synthetic repository with 18 comment-only edits 10 s apart and two quiet minutes after: before, 4 full recomputes and 173 s of CPU; after, no recompute and two load-only checks, 14 s of CPU (the second check is an artefact of the measurement's simulated clock).
  - Deeply nested code no longer drops the file (item 1). Every extractor walks trees recursively, so a 500-branch `else if` chain (JS/TS, C++, Rust) or a 1,000-term `+` chain (every language) raised `RecursionError`; the file was skipped, a live batch kept its old nodes and a fresh scan wrote none. `index_paths` now retries such a file through `dispatch._run_deep`: the same `_index_single_path` call on a thread with a 255 MiB stack (under the 256 MiB Windows allows; 128 MiB was enough for every probe below) and the recursion limit raised to 200,000 meanwhile (one at a time, under a lock; extraction raises before it writes, so the retry is clean). The extractors are unchanged. Measured: a 5,000-term chain plus a 2,000-branch chain extracts in 0.3-0.6 s per file (4 s in JS/TS), and a 150,000-term chain in 6-11 s. A file deeper than even that (Python 3.13+ raises `RecursionError` before the C stack runs out, never a crash; probed with a 500,000-term chain) is skipped as `too deeply nested` with a skip mark (none when the file can no longer be stat'ed), and its nodes are deleted, in a live batch and a full scan alike; so is a file whose retry thread can't be had (`stack_size` or `start` raising `ValueError`, `RuntimeError` or `MemoryError`). Tests: `tests/indexer/test_deep_nesting.py` (all nine languages at 1,000 terms and 500 branches, live equals fresh, the too-deep fallback).
  - Build output folder names are ignored only where a build writes them (item 4; index format 18). `build`, `dist`, `bin`, `obj` and `target` used to be ignored at any depth, so Rust's `src/bin/` binaries and source packages named `build` (pip's `operations/build/`) were never walked, and nothing reported them. They are now `walk.BUILD_OUTPUT_DIR_NAMES`, ignored by `walk.is_build_output` only at the repository root or beside a project manifest (`BUILD_MANIFESTS`: Cargo.toml, pom.xml, Gradle build/settings files, package.json, pyproject.toml, setup.py, setup.cfg, CMakeLists.txt, go.mod, or a `.csproj`/`.fsproj`/`.vbproj`/`.sln`), and `src/bin` never. `vendor`, `worktrees`, virtual environments and caches stay ignored anywhere, and a `.gitignore` still leaves out any folder it names. `is_ignored_path(path, root)` applies the same rule to a repo-relative path, so the walk, `prune_stale_files`, the inotify filter, the watcher's event filter and the resolver configuration agree. The format bump rescans existing graphs so they gain the files. A build manifest created, deleted or renamed is handled like a `.gitignore` edit: `RepoSync` follows the batch with a catch-up (which prunes the files now build output and indexes the ones no longer so), and the watcher asks for a rewatch, so a folder that became source gets its watch and its files offered (one that became build output keeps its watch until the agent restarts, its events dropped, as for a `.gitignore`). `walk._holds_manifest` is cached per folder, cleared by `forget_manifests` at every full scan and catch-up and whenever the watcher sees a manifest change. Tests: `tests/indexer/test_build_output_live.py` (add, then remove, `tools/pyproject.toml` or a `.csproj` beside `tools/dist/gen.py`; live equals fresh each time). The accuracy fuzz has no manifest op: it replays dispatch calls, not `RepoSync`'s catch-up.
  - The dashboard with Neo4j down (item 9). `GET /api/repos` used to answer 500 (it counted each repository's nodes unguarded), so the picker showed only All Repos, and the console showed the driver's raw `ServiceUnavailable` text. `/api/repos` now returns the registry's rows with `node_count: null` and `graph_unavailable` set to the MCP tools' message (`routes.neo4j_down_message`, wrapping `tools.neo4j_unavailable`; one failed count stops the rest), `/api/cypher` answers 503 with `{"code": "Neo4jUnavailable", "message": ...}`, and an app-level handler turns `ServiceUnavailable`/`AuthError` from any other route (summary, schema, search) into 503 `{"detail": message}`. The page shows that message in one banner (`#neo4jDownState`) and still lists the repositories when the boot probe fails.
- MCP answers are compact JSON (audit 6, item 8). The SDK rendered a returned dict with `indent=2`, so about 40% of every answer's characters were indentation. `_served` (`devgraph/mcp/server.py`), the wrapper every built-in, project and global tool is registered through, now returns the `CallToolResult` itself: one text block of `compact_json` (`separators=(",", ":")`, `ensure_ascii=False`, key order kept) and the same JSON-ready data as `structuredContent` (non-JSON values become strings, as the SDK's `fallback=str` did), so the declared output schemas are unchanged. Errors are plain messages and pass through untouched. The `devgraph://project-tools` and `devgraph://tool-catalog` resources are compact too; CLI output (`config tools list --json` and the like) stays indented. Measured on fictional samples: `search_component` (50 rows) 10,247 to 6,931 characters, `find_callers` 1,577 to 969, `god_nodes` (20) 4,547 to 3,051, `describe_node` on a module 1,985 to 1,020. Not done: flattening a one-label `labels` list to a string (a shape change for clients). Tests: `tests/mcp/test_compact_results.py`.
- Full-scan memory (audit 6, item 6). `index_paths` kept every code file's node and edge dicts, and a Python file's text, until pass 2, so a full scan grew by about 120-240 KB a file and freed nothing until its end. They now go into `_Extractions` (`devgraph/indexer/dispatch.py`): each file's `(nodes, rels, content)` is pickled and zlib-compressed into an anonymous temporary file (a few KB a file) before the file's graph write, in `devgraph_home()/tmp` (not the system's temporary folder, tmpfs on some systems; anonymous and deleted on close), and read back by pass 2 and the owning-service pass; a write or read that fails, a full disk say, aborts the batch (`ExtractionSpillFailed`, one of dispatch's `ABORTS_BATCH`) rather than skipping a file, and a file whose graph write fails keeps its earlier extraction or none, and only each node's key fields (label, name, file, owner, mkeys, proj, source) and its Module's `heir_open` stay in memory for the steps between the passes. Pass 2 no longer writes a batch file's nodes again, only its edges: its pass-1 replace wrote them, no other file's replace deletes them (every node an extraction writes is its own or file-less, `test_no_extraction_writes_a_node_another_file_owns`), a shared node keeps the file's claim, and the properties pass 1 leaves out are written by `write_match_keys`/`write_heir_open` with the values the nodes hold; a file-less claimed node (an ASP.NET handler stub) keeps its `mkeys`/`proj` in its pass-1 write, since no match-key write reaches it. A referrer, indexed after those, still has its nodes written again. A router file the mounts pass finds left out after its extraction is dropped from pass 2 rather than written back. Measured with the engine stubbed, on a synthetic Python repository (22 nodes, about 290 edge rows a file): 2,020 files peaked at 566 MB RSS before and 122 MB after (tracemalloc 469 MB and 42 MB), 8,080 files at 2,034 MB and 245 MB, in the same time (34 s and 222 s, extraction-bound); one `upsert_nodes` transaction a file fewer reaches Neo4j. Full scans run one at a time in a process (above), and a batch logs `indexed N / M files` every 5,000 files. Not done: pass 1 still writes one transaction per file and every edge twice (pass 1 and pass 2), and the batch's compact node index, the pre-batch snapshot (`list_file_nodes`) and the path maps still grow with the repository (about 20 KB a file in this benchmark). Tests: `tests/indexer/test_scan_memory.py`; the live check that the graph equals the double write's is `test_pass_two_skipping_a_batch_files_node_writes_leaves_the_same_graph` in `test_graph_accuracy_fuzz.py`.
- Audit 7, MCP answer quality. `search_component` ranks the whole query above its words (item 2): a name equal to any term used to tie with the exact match, so `run_cypher` returned one `cypher` and fourteen `run`s and no `run_cypher`. `_SEARCH_TIER` and `_rank_search_results` now rank the trimmed query as the exact name, then ignoring case, then a name starting with or containing the whole query, then a name equal to, starting with or containing a term; the index stage is unchanged and the dashboard's search box passes the query too. On DevGraph's own graph the exact match is now first for `run_cypher`, `get_source`, `index_paths` and `describe_node` (previously absent, absent, 6th and 2nd).
- Platform-specific tests run on every platform where they can: the Windows junction walk tests simulate junctions on other platforms (a symlinked directory reported as a junction to `os.scandir` and `Path`), and the dashboard's exclusive port bind, `_change_stamp_ns` and the git compare's `kill_after_timeout` choice are tested with the module's `sys.platform` patched. `tests/test_platform_skips.py` fails on any platform skip not listed in its `ALLOWED` table with its reason (real symlinks, file modes or change times, POSIX shell stubs, the process table, inotify, the X11 tray backend). Stubs of DevGraph's own functions go through `tests.helpers.stub`, which binds every call against the real function's signature, so a stub that drifts from it fails on every platform, even where the code under test catches the TypeError.

## Commands

- **Canonical setup**: the README installer launches `.\scripts\setup-menu.ps1`, which creates the Python environment, installs DevGraph, starts Neo4j, initializes schema, runs `devgraph doctor`, and offers MCP client registration. Idempotent.
- **Update an existing checkout**: `devgraph update` — fast-forward pull, reinstall, `doctor`, and tray restart when needed. Commit or stash local changes first; `--force` only suppresses the dirty-tree guard. `.\scripts\update.ps1` remains as a compatibility entry point.
- Manual equivalent (any platform): `uv sync --extra dev` (or `python -m venv .venv` and `python -m pip install -e ".[dev]"` with that environment's Python: `.venv/bin/python` on Linux and macOS, `.venv\Scripts\python` on Windows) → start Neo4j with Podman or Docker (`docker` takes the same arguments):
  `podman run -d --name devgraph-neo4j -p 127.0.0.1:7474:7474 -p 127.0.0.1:7687:7687 -e NEO4J_AUTH=neo4j/devgraph-local-dev -v devgraph_neo4j_data:/data -v devgraph_neo4j_logs:/logs docker.io/library/neo4j:5.26-community`
  (`deploy/podman-compose.yml` is an untested alternative for compose-provider setups.) The README's Linux quickstart walks through the same steps.
- Tests: `uv run pytest` (or the environment's Python with `-m pytest`)
- Continuous integration: `.github/workflows/tests.yml` runs on every push and pull request (and on demand). The Linux job runs the full pytest suite against a Neo4j 5.26 service container, then the `tests/dashboard/*.js` node harnesses. The Windows job runs the same suite and harnesses without live Neo4j: the live tests skip there, so Windows covers everything but the graph round trips.
- CLI: run `devgraph --help` for the authoritative command list. Main groups cover repository registration and rescans; status, diagnostics, stats, and pruning; dashboard and tray control; MCP client setup; configuration (the `config` group: settings, schema list/add/edit/delete/reset, show/validate/eject, tools) and logs; graph export; annotations, mentions, git history, and PR/issue opt-ins; and self-update.

**Podman note**: on Windows, `podman.exe` may not be on PATH by default even when installed — check `%LOCALAPPDATA%\Programs\Podman` first. `devgraph doctor` needs Podman only while Neo4j is unreachable. Never install software to the host; dependencies live in `.venv/` and containers. Never touch containers/volumes not prefixed `devgraph-`.

## Structure

- `Blueprints/` — numbered design docs. `Design Brief #1.md` is the architecture source of truth. `Design Brief #2.md` is an unbuilt Phase 4 sketch. `Implementation Plan #2.md` covers rollout readiness + extraction quality (implemented). `Design Brief #3.md` and `Implementation Plan #3.md` cover response envelopes, `CALLS` scope narrowing, `impact_analysis_for_diff`, and a deferred embedding-search item (implemented except the deferred item). `Implementation Plan #5.md` covers the live dashboard (implemented).
- `devgraph/config/` — Pydantic settings; all security-sensitive defaults off (telemetry, cloud sync, cross-repo, `run_cypher`). `project_tools.py` loads and fail-closed-validates an optional repository-root `devgraph.tools.yaml` declaring read-only Cypher tools (served to MCP clients by `devgraph/mcp/tool_plane.py`). `project_schema.py` loads and fail-closed-validates an optional repository-root `devgraph.schema.yaml` declaring extra node types/relationships — the loader feeds the filesystem provider (`devgraph/indexer/providers/filesystem.py`), which indexes declared File/Folder-style node types and parent edges, and the docs provider (`devgraph/indexer/providers/docs.py`), which indexes node types and relationships from Markdown front matter; custom providers are still validated as data only and never run, and a repository without the file resolves to exactly the built-in labels, relationship types, and constraints.
- `devgraph/registry/` — SQLite-backed repo allowlist (`RepoRegistry`), thread-safe via `RLock`. Stores `docs_path`, `mentions_enabled`, PR/issue opt-in flags, `last_indexed_commit`.
- `devgraph/analytics/` — derived graph analytics: `insights.py`.
- `devgraph/graph/` — `GraphEngine` (Neo4j driver, idempotent MERGE, schema constraints, per-file delete cleanup) and `schema.py` (canonical labels/relationship types — import from here, don't hardcode strings).
- `devgraph/indexer/common.py` — `GraphNode`/`GraphRelationship`/`ExtractionResult`, shared by every language extractor below.
- `devgraph/indexer/python/` — Tree-sitter Python extractor. Modules keyed by repo-relative path. Extracts `CALLS` (resolved through scope and imports, with `confidence` and `caller_class` metadata for `find_callers`), `CONTAINS`, `IMPORTS` (every candidate file under the importer's ancestor directories; `resolve.py`), `EXTENDS`, docstrings (`description`/`docstring_full`), and `start_line`/`end_line` for `get_source`.
- `devgraph/indexer/jsts/`, `csharp/`, `cpp/`, `java/`, `rust/`, `go/` — Implementation Plan #8's six additional Tree-sitter extractors, same node/edge shape as the Python one. Since index format 8 every one of them resolves `CALLS` and `IMPORTS` through its language's own rules (see the call-resolution entries above); C++ reads quoted includes without the build's `-I` flags. JS/TS covers `.js`/`.jsx`/`.mjs`/`.cjs`/`.ts`/`.tsx`/`.mts`/`.cts`; an import with an explicit extension resolves to the source that emits it (`./x.js` to `x.ts`/`x.tsx`/`x.js`, `.mjs` to `.mts`, `.cjs` to `.cts`, then `x.js/index.*` for a directory); a `?query` or `#fragment` is dropped first. Candidates are not checked against the disk, so `./x.js` links both `x.ts` and `x.js` when both exist.
- `devgraph/indexer/kotlin/` — Kotlin Tree-sitter extractor (added after Plan #8's six), mirroring the Java extractor. Maps `class`/`interface`/`enum class`/`sealed`/`data`/`object` to Class, `fun` to Function, resolves `import` via Kotlin's package/folder convention; since index format 7 an import is an `IMPORTS` edge to the class or top-level function it names, in its package's directory (see the extractor's module docstring for the known-limitations list). Declarations after a one-line class body, which tree-sitter-kotlin 1.1.0 loses, are recovered (`_parse_kotlin`). `.kts` build scripts are intentionally not indexed.
- `devgraph/indexer/containers/`, `apis/`, `datastores/` — Podman Compose, route, and datastore-usage extractors (Python's `DatastoreExtractor`; `client_datastores` for JS/TS, Java, Kotlin, C# and Go). Container extractor captures `build_context` for service cross-linking, and a compose service's `depends_on` (list or map) and `links` (`name:alias` stripped) as `Service` `DEPENDS_ON` `Service`, both ends pinned to the compose file, so `get_service_dependencies`, `impact_analysis` and `find_dependency_cycles(relationship="DEPENDS_ON")` see them. Gaps: a compose file's `include:` and a service's `extends:` are not followed, an override file (`compose.override.yaml`, `-f a -f b`) is indexed as its own file rather than merged, and a dependency on a service declared in another compose file gets no edge (both ends are pinned to the declaring file).
- `devgraph/indexer/dispatch.py` — routes changed/deleted files to the right extractor (`index_paths`, `remove_paths`, `full_scan`); called by CLI, watcher, and tray app. Prunes stale nodes on re-index; links services to owning code via `build_context`.
- `devgraph/indexer/docs/` — Markdown front-matter extractor for `Requirement`/`DesignDecision`/`ArchitectureNote`.
- `devgraph/indexer/mentions/` — Markdown mention extractor detecting known entity references in code-like contexts (inline code, fenced blocks, call syntax `Name(`, declaration keywords); creates `Document` nodes and `MENTIONS` edges; configurable ambiguous-name handling via `mentions_ambiguous_mode` setting (`"all"`/`"skip"`).
- `devgraph/indexer/git_history/` — commit history via GitPython (local only). Automatically synced on every `.git` state change (branch switches, rebases, resets) via a dedicated watcher, including correct reconciliation of orphaned commits when history is rewritten. Stages denormalized recency properties onto `Module`/`Function`/`Class` nodes (via `git blame` for function/class-level `last_modified_at`); no `Function`/`Class`-level `created_at` (intentionally, since it would require `git log -L` which is too fragile). Author tracking via `git_recency_track_author` setting (off by default). Recency only annotates nodes that already exist (`stage_recency`/`set_recency` MATCH rather than MERGE), so a commit touching a README, an image or a deleted file no longer leaves a bare `Module` behind. So that the sync never reaches a file before the indexer does, the agent runs it after a git operation's catch-up, in the same job under the repository's batch lock (a CLI `rescan` indexes first, then syncs). Upgrade cleanup: `prune_stale_files` (every `full_scan`, and the agent's catch-up on start) deletes `Module` nodes with no `source_file`, `file` or `path`, which only the old MERGE made.
- `devgraph/indexer/pr_issues/` — opt-in GitHub PR/issue ingestion; hard-gated per-repo, off by default. With the flag off, `find_related_prs`/`issue_history_for` return an empty envelope with a `notice` (the old `gh` CLI fallback is gone: no tool reaches the network).
- `devgraph/watcher/` — `WatcherManager`, registry-scoped file and git-state watching with debounce. Watches `.git` and `.git/refs` non-recursively (HEAD, `packed-refs`, `index.lock`, `refs/stash`) and `.git/refs/heads/` recursively to detect branch switches/rebases/resets/stashes, triggering automatic history reconciliation after the post-git catch-up; handles atomic rename-saves correctly. A file rename queues the source as deleted and the destination as changed; directory deletes and moves queue the folder (expanded to exact files by `remove_paths`), and directory creates and in-repo moves are walked with `walk.indexable_paths_under`, one log line per folder. A create, delete or move at the top level asks for a watch reconcile on its own timer thread, which drops dead or stale watches (checked by emitter liveness and directory identity), schedules missing folders and walks them, retrying a failed schedule after 0.5, 1, 2 and 4 s before warning. Each repository has one batch lock (`run_exclusive`), shared with catch-ups, the schema rescan and dashboard registration; `on_changes` runs outside the handler's event lock. On start (and Resume, and a repository picked up by `refresh`), `last_indexed` is read before the watch starts and `on_catch_up` runs under the batch lock. A git burst (an `index.lock` tied to a HEAD or ref change) asks for a catch-up 2 s later from the burst's start, followed by the git-history sync in the same job; `request_catch_up` coalesces requests to the earliest `since`, and a request with a shorter delay replaces a pending one. Timers come from an injectable `timer_factory`. Design: `docs/superpowers/specs/2026-10-07-watcher-correctness-design.md`.
- `devgraph/mcp/` — MCP query implementations (`tools.py`) + server wiring (`server.py`). Most list-valued tools return `{count, results, truncated}` envelopes capped by `max_results`. All tools are read-only except `run_cypher` (gated behind config, off by default); built-in tools query through `_query` (`GraphEngine.run_read_cypher`: read access, `BUILTIN_TIMEOUT_S` = 30 s, a timeout raised as a ToolError), and so do `key_nodes`/`find_communities` through `insights.top_nodes`/`community_members`; `find_callers`, `find_mentions`, `list_recent_changes`, `blame_component`, `find_requirements_for`, `explain_architecture` and `list_endpoints` read at most `LIST_ROW_LIMIT` = 10,000 rows, and past it the envelope is `truncated` with a `notice` instead of failing, and impact traversal is bounded at `IMPACT_MAX_DEPTH` = 4 hops, expanded hop by hop over distinct nodes (each dependent listed at its nearest hop) rather than by variable-length paths, so a common name like `get` answers in well under a second instead of timing out. `tool_plane.py` resolves the session repository and registers the repository's `devgraph.tools.yaml` tools; built-in tools default `repo_id` to that session repository; `devgraph://project-tools` reports the scope, served tools and notices. Serves `devgraph://client-guide` and the generated `devgraph://tool-catalog` resource for client handover. Auto-starts/stops the tray app via refcounted holder tracking on connect/disconnect.
- `devgraph/cli/` — Typer CLI; see Commands above. `status` exits 1 when Neo4j or the registry is unusable and `add` when its initial scan fails; a Neo4j failure is one line naming the setting and the `.env` file to fix (`_neo4j_problem`); `remove --keep-graph` unregisters without Neo4j (then `devgraph prune` deletes the graph data once Neo4j is up); a registry SQLite error names the registry file.
- `devgraph/agent/` — `lifecycle.py`: PID-file/liveness/holder-refcounting for the tray app, shared by CLI and MCP server. `tray.py`: pystray shell wiring watcher + indexer + Neo4j health check + heartbeat file + the dashboard's own daemon thread. `sync.py`: `RepoSync`, shared by the tray and `headless.py`, indexes live batches, runs catch-ups (`dispatch.catch_up`: prune, then re-index files the graph doesn't know or whose change stamp is at or after `since` minus 5 s), stamps `last_indexed` with the start of the work, and on a failure holds the stamps back to a per-repository floor, warns, and asks for a catch-up 30 s later (and again when the health loop sees Neo4j recover). It publishes `catch_up` events (`running`, then `done` or `failed`) that drive the tray's `DevGraph (catching up)` tooltip and the dashboard pill.
- `devgraph/dashboard/` — FastAPI app (`app.py`: `build_app()`), `/api/*` read + Cypher-proxy routes (`routes.py`, backed by `GraphEngine.run_cypher_graph`), dashboard-shaped Cypher helpers (`queries.py`), real git log/status (`git_info.py`), in-memory query telemetry for the dashboard's own Cypher console (`query_log.py`), database and memory readings plus their sampled history (`db_metrics.py`), a read-only view of MCP tool-call metadata recorded by the MCP server processes (`/api/mcp-telemetry`, read from the local store `devgraph/mcp/server.py` appends to — never through the MCP stdio server), SSE pub/sub (`events.py`: `EventBroadcaster`), the agent's server start (`serving.py`: binds the port itself, so a port another program holds is a logged warning, a tray tooltip and a `devgraph status` line instead of uvicorn's silent exit; `GET /api/health` identifies the server, and `devgraph dashboard` refuses to open a port that doesn't answer as DevGraph), and `static/index.html` (single hand-written file, no build step, Cytoscape.js vendored under `static/vendor/`). A second, independent read-only consumer of the same `GraphEngine`/`RepoRegistry` the tray owns — never routes through the MCP stdio server.
- `tests/` — mirrors the `devgraph/` package.
- `deploy/podman-compose.yml` — declarative alternative to the `podman run` setup command.
- `DEVGRAPH-CLIENT.md` — portable doc for another repo's coding assistant to connect to this DevGraph instance.
