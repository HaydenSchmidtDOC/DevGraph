# Project status

## Summary

- Phases 1-3 complete and verified (registry, graph engine, Python indexer, container/API/datastore extractors, watcher, CLI, tray app, docs extractor, git/PR/issue history). Phase 4 (enterprise federation) is design-only, intentionally unbuilt.
- Implementation Plan #5 (live web dashboard) shipped: a FastAPI+uvicorn server on its own daemon thread inside the tray process, serving a single hand-written HTML/CSS/JS file (`static/index.html`, Cytoscape.js loaded from CDN) at `http://127.0.0.1:8765` with live push over Server-Sent Events. It is loopback-only with no authentication (single-user local tool). Graph exploration remains read-only; repository registration is the dashboard's bounded write action and runs the same initial scan as the CLI. The browser never holds Neo4j credentials — every graph query goes through a backend proxy (`POST /api/cypher` and related routes) running against the same `GraphEngine` the tray/watcher/MCP server use. Git history, query telemetry, and settings panes are backed by real data (`git_info.py`, `query_log.py`). The Query telemetry card's MCP half is wired to `GET /api/mcp-telemetry` and shows real tool-call totals, top tools, nearest-rank P50/P95/P99 latency and error rate over the newest 500 records the MCP server wrote (metadata only — no query text or arguments; a project tool is recorded as `<repo_id>_<name>`, a global one as `gl_<name>`, a built-in by its bare name, each with an origin), read from a local file so the card works with Neo4j down. That endpoint cannot tell an empty store from a missing or unreadable one, so those rows stay dashed and labelled in both cases instead of reporting zeros, and each figure discloses the sample it was computed over. Of the card's Neo4j rows, active queries is attempted live via `SHOW TRANSACTIONS` and queued transactions has no source on this build. The Database & memory card is backed by `dashboard/db_metrics.py`: a 15-second sampler (one hour in memory) reading heap, RAM, swap, CPU and GC from the JVM's own JMX beans, the configured page cache size from `dbms.listConfig`, and store size from a walk of `DEVGRAPH_NEO4J_DATA_DIR`; each group is independently live or labelled unavailable, and page cache hit ratio has no source on Community. The force-directed graph settle uses a Barnes-Hut quadtree for repulsion, and query highlighting can dim non-matching entities without rebuilding the canvas.
- Implementation Plan #6 (Markdown mentions indexing) shipped: per-repo opt-in detection of known entity references appearing in code-like contexts (inline code, fenced blocks, call syntax, declaration keywords) within Markdown files, creating `Document` nodes and `MENTIONS` edges, queryable via `find_mentions` MCP tool; ambiguous-name handling configurable via `mentions_ambiguous_mode` setting.
- Implementation Plan #7 (automatic git-history sync + recency staging) shipped: Git commit history is now automatically kept in sync whenever `.git` changes (branch switches, rebases, resets), including correct handling of orphaned commits — no manual `index-history` command needed once a repo has been indexed at least once via `--full`. `Module`/`Function`/`Class` nodes get denormalized recency properties (`created_at`/`last_modified_at` staged from git blame), queryable via the new `list_recent_changes` MCP tool or filtered on `find_callers`/`search_component` via `modified_within_commits`. Author tracking opt-in via `git_recency_track_author` setting.
- Implementation Plan #8 (multi-language extraction) shipped: source extraction is no longer Python-only. Tree-sitter extractors under `devgraph/indexer/jsts/`, `csharp/`, `cpp/`, `java/`, `rust/`, and `go/` dispatch by file extension alongside Python, dynamically per file rather than one language per repo, sharing `Module`/`Class`/`Function`/`CONTAINS`/`CALLS`/`IMPORTS`/`EXTENDS` node/edge shapes through `devgraph/indexer/common.py`. Each was checked against a real public project before merge. C++ is deliberately structural-only because reliable `#include` resolution needs build-system context; the other languages use best-effort same-repository import guesses. See `.claude/skills/adding-a-language/SKILL.md` and `Blueprints/Implementation Plan #8.md` for the process and language decisions.
- Hardening pass (crash/instability quick wins) shipped: `index_paths` no longer aborts a whole batch on one bad file — each file is extracted in its own guarded step (`_index_single_path`) and logged/skipped on failure. The tray's health-check loop, quit/pause/dashboard-open paths, and `main()` are all exception-guarded so a background-thread or startup failure can't silently take down the watcher/indexer or leave a stale PID file. `GraphEngine` retries transient Neo4j errors (`ServiceUnavailable`/`SessionExpired`/`TransientError`) with bounded exponential backoff on every idempotent write and `verify_connectivity` (arbitrary `run_cypher`/`run_cypher_graph` queries are deliberately not retried). `RepoRegistry` uses WAL journal mode, a 5s `busy_timeout` for cross-process access, and an idempotent `close()`. Git-history sync and the dashboard's git-status/log paths tolerate empty repos (no commits yet) and commits with no author/message. Removed dead code in `dashboard/routes.py` that would have raised `NameError`.
- Second hardening pass shipped: `devgraph remove` now calls `GraphEngine.delete_repository` before dropping the SQLite registry row, so a removed repo's Neo4j nodes don't orphan forever. `full_scan` no longer aborts entirely on a file the OS can't stat (locked file, broken symlink, Windows reparse point) — Python 3.13's `Path.is_file()` stopped swallowing `OSError`, so that one file is now skipped and logged instead. The dashboard's repo dropdown reads `/api/repos` (backed by the registry) instead of querying `:Repository` nodes directly, so pre-fix orphaned nodes no longer appear as live repos. Tray app: unhandled `pystray` exceptions are now caught (previously a silent crash), and the tray icon has an explicit "Open Dashboard" menu item (its status-text line is also clickable).
- `devgraph config` command group (#1, CLI slice) shipped: `config settings` (bare `config` unchanged; secrets now masked), `config show` (effective schema with per-entry origin), `config validate` (fail-closed, `--all` with cross-repository conflicts, CI-friendly exit codes) and `config eject` (commented starter `devgraph.schema.yaml`; refuses to overwrite). `config enable/disable` and `config tools` have since shipped (see below); `config schema` editing has since shipped (see below).
- Node-identity collision fixed: `Function`/`Class`/`Service`/`Container`/`Volume` MERGE on `(repo_id, name, file)` when `file` is set, so two files defining a same-named function/class (or two compose files defining the same service) no longer collapse into one node (`get_source`, `find_callers`, `identity_key` all key off the same `_is_file_scoped` predicate — see [HANDOVER_node_identity.md](HANDOVER_node_identity.md)). Same-file sibling collisions (two classes in one file with same-named methods) remain open, deliberately deferred.
- Data-loss fix: `delete_nodes_by_source_file` used to `DETACH DELETE` any node whose `source` property matched the edited file — wrong for nodes several files legitimately co-produce (e.g. a `Service` defined in both `docker-compose.yml` and an override file), which destroyed the node outright when either file was edited. Those nodes (the ones without a `file` property — `Container`/`Service`/`Network`/`Volume`/API/Database-ish) now accumulate every producing file into a `sources` property on upsert; deleting a file unclaims it from `sources`, and the node is only removed once no file claims it.
- MCP tools live over stdio (`devgraph/mcp/server.py`), including `impact_analysis_for_diff`, `find_mentions`, `list_recent_changes`, `god_nodes`, and `describe_node`. The server exposes the authoritative list as `devgraph://tool-catalog`.
- `devgraph register` (`add` is an alias) and `rescan` run a real full scan via `devgraph/indexer/dispatch.py`; the watcher and tray app route live changes through the same dispatcher, including delete cleanup across all supported languages.
- Within one `index_paths` batch (a full scan, or a watcher batch), cross-file edges do not depend on file order: every file's nodes are written first, then source-file edges, docs-note edges (`SUPERSEDES`/`DECIDED_BY`/`links`), and Markdown `MENTIONS` are resolved against the whole batch. A node several files produce (a `Datastore`, `Endpoint` or `Container` written with a `source`) no longer depends on write order either: it keeps each claiming file's properties (`claims`, JSON with sorted keys), `sources` stays sorted, and the node's properties are those of the alphabetically first source, re-attributed when that file stops claiming it. This changed from last-writer-wins, so a full scan now gives the first file's properties where it used to give the last one's. Across batches, a batch also re-indexes files outside it that refer by name to a node it adds (compared with what its files produced before): docs notes whose `SUPERSEDES`/`DECIDED_BY`/`links` name it, route files with a handler stub of a new Function's name, and same-directory, same-extension Java/Kotlin files naming a new class. Markdown that mentions an added name (when mentions are enabled) gains `MENTIONS` edges to just the added names rather than a full re-index; for a name that already exists elsewhere these files come from existing `MENTIONS` edges, and only names new to the graph need a text scan. At most 25 files are relinked per batch, and the rest wait for a rescan. Direct importers of a changed `.py`/`.java` file are re-indexed as before. Remaining gaps: other by-name referrers indexed before their target existed — e.g. an `IMPORTS` of a newly added module, a supertype in another directory, or `CALLS` from outside the batch — stay unlinked until re-indexed or rescanned. Deletions don't relink either (e.g. an ambiguous name that `skip` mode left unlinked stays unlinked after the duplicate is removed). Likewise, in `skip` mode, adding a second node with an already-mentioned name leaves the existing `MENTIONS` edges in place until a rescan (a full re-index of the doc behaves the same; only a rescan drops them).

- Declarative providers, slice 1: Markdown front matter (#1) shipped. A node type can declare `source: {provider: docs, paths, where?, fields?}` and a relationship `provider: docs` with a `field`: matching Markdown files become nodes keyed by repo-relative `path` or, since the front-matter keys slice below, by one front-matter field (tagged `extractor = "docs"`, with the owning file in `path`), filled from front matter through plain text conditions (`is`, `starts_with`, `contains`, `like`; no regexes) and a property-to-key map, and linked to every `to` node whose `name` equals the field's value (Services fan out across compose files). Globs are matched segment by segment with `fnmatchcase` (no backtracking), reads are bounded, and the provider fails closed on an invalid or pending schema. `devgraph/indexer/providers/docs.py` does the selection and mapping; `index_paths`/`remove_paths`/`full_scan` keep the nodes and edges current, a schema edit is applied by the existing rescan (stale edges, properties and nodes cleared), and a batch that adds a targeted node relinks the docs files that name it. `devgraph doctor` reports matched files, condition-excluded files, entries and per-file problems, plus values that match no node when Neo4j is up; `config schema list` and the Config page form (Paths, Conditions, a Front-matter key per field and per relationship) cover it, and the starter template's example is a Runbook. See `docs/superpowers/specs/2026-10-06-declarative-providers-design.md`. Front-matter keys are done too: a docs type's key is `[path]` or one string field read from front matter (`key: [adr_id]`, `fields: {adr_id: id}`), so a link can say `supersedes: ADR-012`. One owner map per batch, computed from every file on disk, decides which file owns each id (the original beats editor copies by a stem-aware path order), so renames keep the node and its links, a re-id or delete hands the id to the next claimant, and doctor names duplicates, missing ids, links by path and key conflicts between repositories; the Config form ticks Key on the field. See `docs/superpowers/specs/2026-10-06-docs-frontmatter-keys-design.md`. A docs read cache keeps each file's parsed front matter in process while its stat identity is unchanged, so a save parses only the files changed since they were last read (the batch's own files always fresh, a full scan forgets the repository first); see `docs/superpowers/specs/2026-10-07-docs-read-cache-design.md`. The walk behind it resolves the repository root once and resolves only symlinked files, keying the rest lexically, and skips ignored directories rather than walking into them; a warm save at 2,000 id-keyed files went from about 0.6 s to about 0.4 s, and the walk still dominates it. It descends into a Windows junction only when the junction's target is inside the repository and not under an ignored directory (so `full_scan` no longer crashes in `prune_stale_files` on a junction pointing outside). `_disk_files` and `prune_stale_files` key files through that walk with the root resolved once. `devgraph doctor` keys its docs file list through the same walk (`docs.files_by_rel`), so it resolves the root once and only links, and agrees with the indexer on symlinks into ignored directories. Still open: the `git` and `ast` providers, relinking a Folder target created later (it links at the next rescan), and the O(matched files) re-read when a batch adds a node of any label a docs relationship targets (every file any docs type selects is walked and checked again, though unchanged ones come from the read cache).
- Watcher correctness (#1) shipped: a running agent keeps a repository's graph equal to a fresh `full_scan` through file renames, and folder moves, renames and deletes (top-level folders included), edits made while it was off, and git checkouts and pulls. File renames are a delete plus a create; directory events are walked or expanded to exact file paths by `remove_paths`; top-level folder changes reconcile the watches; batches, catch-ups, the schema rescan and dashboard registration share one lock per repository; every `last_indexed` stamp is the start of the work it covers; the agent catches up incrementally on start and after a git operation, and retries a failed batch from a held-back floor (the last good stamp). Every successful catch-up (start, resume, post-git, retry) of a repository with a `.git` folder is followed by the git-history sync in the same locked job, so a commit whose post-git job a stop or pause cancelled, or one made while the agent was off, is synced on the next start. Docs notes under `docs_path` record their repo-relative path as `source_file` (they used the bare filename, so every catch-up pruned and recreated them, a live delete left the note behind, and two notes with the same filename in different folders shared one key); on a graph written before this, the next catch-up or rescan deletes every note whose `source_file` is outside the docs path (an upgrade cleanup in `prune_stale_files`, like the bare-Module one; skipped when the docs path is the repository root, where a bare key can't be told from a root-level note) and writes the notes again under their repo-relative path, so none is duplicated or lost, mentions on or off, and a bare key that names a real root file (`README.md` for `docs/README.md`) goes too, with its edges. A catch-up counts a docs-routed file as known only when a note holds its key (its mentions `Document` holds the same key). Before a dead watchdog emitter is stopped again (unscheduled by the reconcile, or by the observer's stop), its closed Windows directory handle is forgotten: watchdog keeps the value and would close it a second time, by then perhaps another object's handle. The tray tooltip reads `DevGraph (catching up)` and the dashboard's Entities pill `Catching up…` while that runs. `tests/watcher/test_watcher_live.py` checks each scenario against a fresh scan, properties included. See `docs/superpowers/specs/2026-10-07-watcher-correctness-design.md`. Still open, each fixed by `devgraph rescan`: a modified existing file whose events were dropped outside a git operation; a file changed while the agent was off whose timestamps all predate the last update by more than 5 s (a clock moved back, a skewed network share, a Windows tool that restores the mtime); a top-level folder left unwatched once its schedule retries are used up (until the next top-level change or restart); the by-name cross-batch referrer gaps above; `devgraph add`/`rescan` in another process not serialised with the agent; macOS (FSEvents) unsupported as an agent platform; linked worktrees and submodules (a `.git` file) get no post-git catch-up or git-history sync, only the catch-up on start. The first git-history sync of a repository (registered without `--full`) reads its whole history in one job under the batch lock, so live updates wait for it: about 90 s at 400 commits and nearly 6 minutes at 5,000; the agent logs `Reading the git history of <repo> for the first time (N commits); live updates resume when it finishes` before it starts. Still to do: chunk the initial git sync so the batch lock is released between chunks. Not fixed by a plain rescan: a Module deleted and restored (`rm a.py; git checkout -- a.py`) loses its recency and `MODIFIES` edges until `devgraph rescan --full`. Pre-existing bugs found by the watcher fuzz, also present before this slice: a service removed from a compose file stays in the graph, even after a full scan; a mention removed from a Markdown file keeps its `MENTIONS` edge, even after a full scan; deleting and restoring an import target loses the `IMPORTS`/`CALLS` edges pointing at it (the known cross-batch referrer gap, which branch switches hit) until a rescan.

## Commands

- **Canonical setup**: the README installer launches `.\scripts\setup-menu.ps1`, which creates the Python environment, installs DevGraph, starts Neo4j, initializes schema, runs `devgraph doctor`, and offers MCP client registration. Idempotent.
- **Update an existing checkout**: `devgraph update` — fast-forward pull, reinstall, `doctor`, and tray restart when needed. Commit or stash local changes first; `--force` only suppresses the dirty-tree guard. `.\scripts\update.ps1` remains as a compatibility entry point.
- Manual equivalent: `python -m venv .venv` → `.venv/Scripts/python -m pip install -e ".[dev]"` → start Neo4j:
  `podman run -d --name devgraph-neo4j -p 127.0.0.1:7474:7474 -p 127.0.0.1:7687:7687 -e NEO4J_AUTH=neo4j/devgraph-local-dev -v devgraph_neo4j_data:/data -v devgraph_neo4j_logs:/logs docker.io/library/neo4j:5.26-community`
  (`deploy/podman-compose.yml` is an untested alternative for compose-provider setups.)
- Tests: `.venv/Scripts/python -m pytest`
- Continuous integration: `.github/workflows/tests.yml` runs on every push and pull request (and on demand). The Linux job runs the full pytest suite against a Neo4j 5.26 service container, then the `tests/dashboard/*.js` node harnesses. The Windows job runs the same suite and harnesses without live Neo4j: the live tests skip there, so Windows covers everything but the graph round trips.
- CLI: run `devgraph --help` for the authoritative command list. Main groups cover repository registration and rescans; status, diagnostics, stats, and pruning; dashboard and tray control; MCP client setup; configuration (the `config` group: settings, schema list/add/edit/delete/reset, show/validate/eject, tools) and logs; graph export; annotations, mentions, git history, and PR/issue opt-ins; and self-update.

**Podman note**: `podman.exe` may not be on PATH by default even when installed — check `%LOCALAPPDATA%\Programs\Podman` first. Never install software to the host; dependencies live in `.venv/` and containers. Never touch containers/volumes not prefixed `devgraph-`.

## Structure

- `Blueprints/` — numbered design docs. `Design Brief #1.md` is the architecture source of truth. `Design Brief #2.md` is an unbuilt Phase 4 sketch. `Implementation Plan #2.md` covers rollout readiness + extraction quality (implemented). `Design Brief #3.md` and `Implementation Plan #3.md` cover response envelopes, `CALLS` scope narrowing, `impact_analysis_for_diff`, and a deferred embedding-search item (implemented except the deferred item). `Implementation Plan #5.md` covers the live dashboard (implemented).
- `devgraph/config/` — Pydantic settings; all security-sensitive defaults off (telemetry, cloud sync, cross-repo, `run_cypher`). `project_tools.py` loads and fail-closed-validates an optional repository-root `devgraph.tools.yaml` declaring read-only Cypher tools (served to MCP clients by `devgraph/mcp/tool_plane.py`). `project_schema.py` loads and fail-closed-validates an optional repository-root `devgraph.schema.yaml` declaring extra node types/relationships — the loader feeds the filesystem provider (`devgraph/indexer/providers/filesystem.py`), which indexes declared File/Folder-style node types and parent edges, and the docs provider (`devgraph/indexer/providers/docs.py`), which indexes node types and relationships from Markdown front matter; custom providers are still validated as data only and never run, and a repository without the file resolves to exactly the built-in labels, relationship types, and constraints.
- `devgraph/registry/` — SQLite-backed repo allowlist (`RepoRegistry`), thread-safe via `RLock`. Stores `docs_path`, `mentions_enabled`, PR/issue opt-in flags, `last_indexed_commit`.
- `devgraph/analytics/` — derived graph analytics: `insights.py`.
- `devgraph/graph/` — `GraphEngine` (Neo4j driver, idempotent MERGE, schema constraints, per-file delete cleanup) and `schema.py` (canonical labels/relationship types — import from here, don't hardcode strings).
- `devgraph/indexer/common.py` — `GraphNode`/`GraphRelationship`/`ExtractionResult`, shared by every language extractor below.
- `devgraph/indexer/python/` — Tree-sitter Python extractor. Modules keyed by repo-relative path. Extracts `CALLS` (name-based, with `caller_class` metadata for `find_callers(scope_to_class=...)`), `CONTAINS`, `IMPORTS` (relative + absolute-dotted-intra-repo resolution), `EXTENDS`, docstrings (`description`/`docstring_full`), and `start_line`/`end_line` for `get_source`.
- `devgraph/indexer/jsts/`, `csharp/`, `cpp/`, `java/`, `rust/`, `go/` — Implementation Plan #8's six additional Tree-sitter extractors, same node/edge shape as the Python one. Import resolution is a same-repo best-effort guess per language's dominant convention (namespace/package/module-path-to-folder), except C++ which is intentionally structural-parity-only (no reliable `#include` resolution without a build system).
- `devgraph/indexer/kotlin/` — Kotlin Tree-sitter extractor (added after Plan #8's six), mirroring the Java extractor. Maps `class`/`interface`/`enum class`/`sealed`/`data`/`object` to Class, `fun` to Function, resolves `import` via Kotlin's package/folder convention. Top-level-symbol imports (e.g. `import a.b.someFunction`) are best-effort only — Kotlin freely puts multiple top-level functions/values per file, so the import names a symbol, not a file (see the extractor's module docstring for the full known-limitations list). `.kts` build scripts are intentionally not indexed.
- `devgraph/indexer/containers/`, `apis/`, `datastores/` — Podman Compose, route, and datastore-usage extractors. Container extractor captures `build_context` for service cross-linking.
- `devgraph/indexer/dispatch.py` — routes changed/deleted files to the right extractor (`index_paths`, `remove_paths`, `full_scan`); called by CLI, watcher, and tray app. Prunes stale nodes on re-index; links services to owning code via `build_context`.
- `devgraph/indexer/docs/` — Markdown front-matter extractor for `Requirement`/`DesignDecision`/`ArchitectureNote`.
- `devgraph/indexer/mentions/` — Markdown mention extractor detecting known entity references in code-like contexts (inline code, fenced blocks, call syntax `Name(`, declaration keywords); creates `Document` nodes and `MENTIONS` edges; configurable ambiguous-name handling via `mentions_ambiguous_mode` setting (`"all"`/`"skip"`).
- `devgraph/indexer/git_history/` — commit history via GitPython (local only). Automatically synced on every `.git` state change (branch switches, rebases, resets) via a dedicated watcher, including correct reconciliation of orphaned commits when history is rewritten. Stages denormalized recency properties onto `Module`/`Function`/`Class` nodes (via `git blame` for function/class-level `last_modified_at`); no `Function`/`Class`-level `created_at` (intentionally, since it would require `git log -L` which is too fragile). Author tracking via `git_recency_track_author` setting (off by default). Recency only annotates nodes that already exist (`stage_recency`/`set_recency` MATCH rather than MERGE), so a commit touching a README, an image or a deleted file no longer leaves a bare `Module` behind. So that the sync never reaches a file before the indexer does, the agent runs it after a git operation's catch-up, in the same job under the repository's batch lock (a CLI `rescan` indexes first, then syncs). Upgrade cleanup: `prune_stale_files` (every `full_scan`, and the agent's catch-up on start) deletes `Module` nodes with no `source_file`, `file` or `path`, which only the old MERGE made.
- `devgraph/indexer/pr_issues/` — opt-in GitHub PR/issue ingestion; hard-gated per-repo, off by default.
- `devgraph/watcher/` — `WatcherManager`, registry-scoped file and git-state watching with debounce. Watches `.git` and `.git/refs` non-recursively (HEAD, `packed-refs`, `index.lock`, `refs/stash`) and `.git/refs/heads/` recursively to detect branch switches/rebases/resets/stashes, triggering automatic history reconciliation after the post-git catch-up; handles atomic rename-saves correctly. A file rename queues the source as deleted and the destination as changed; directory deletes and moves queue the folder (expanded to exact files by `remove_paths`), and directory creates and in-repo moves are walked with `walk.indexable_paths_under`, one log line per folder. A create, delete or move at the top level asks for a watch reconcile on its own timer thread, which drops dead or stale watches (checked by emitter liveness and directory identity), schedules missing folders and walks them, retrying a failed schedule after 0.5, 1, 2 and 4 s before warning. Each repository has one batch lock (`run_exclusive`), shared with catch-ups, the schema rescan and dashboard registration; `on_changes` runs outside the handler's event lock. On start (and Resume, and a repository picked up by `refresh`), `last_indexed` is read before the watch starts and `on_catch_up` runs under the batch lock. A git burst (an `index.lock` tied to a HEAD or ref change) asks for a catch-up 2 s later from the burst's start, followed by the git-history sync in the same job; `request_catch_up` coalesces requests to the earliest `since`, and a request with a shorter delay replaces a pending one. Timers come from an injectable `timer_factory`. Design: `docs/superpowers/specs/2026-10-07-watcher-correctness-design.md`.
- `devgraph/mcp/` — MCP query implementations (`tools.py`) + server wiring (`server.py`). Most list-valued tools return `{count, results, truncated}` envelopes capped by `max_results`. All tools are read-only except `run_cypher` (gated behind config, off by default). `tool_plane.py` resolves the session repository and registers the repository's `devgraph.tools.yaml` tools; built-in tools default `repo_id` to that session repository; `devgraph://project-tools` reports the scope, served tools and notices. Serves `devgraph://client-guide` and the generated `devgraph://tool-catalog` resource for client handover. Auto-starts/stops the tray app via refcounted holder tracking on connect/disconnect.
- `devgraph/cli/` — Typer CLI; see Commands above.
- `devgraph/agent/` — `lifecycle.py`: PID-file/liveness/holder-refcounting for the tray app, shared by CLI and MCP server. `tray.py`: pystray shell wiring watcher + indexer + Neo4j health check + heartbeat file + the dashboard's own daemon thread. `sync.py`: `RepoSync`, shared by the tray and `headless.py`, indexes live batches, runs catch-ups (`dispatch.catch_up`: prune, then re-index files the graph doesn't know or whose change stamp is at or after `since` minus 5 s), stamps `last_indexed` with the start of the work, and on a failure holds the stamps back to a per-repository floor, warns, and asks for a catch-up 30 s later (and again when the health loop sees Neo4j recover). It publishes `catch_up` events (`running`, then `done` or `failed`) that drive the tray's `DevGraph (catching up)` tooltip and the dashboard pill.
- `devgraph/dashboard/` — FastAPI app (`app.py`: `build_app()`), `/api/*` read + Cypher-proxy routes (`routes.py`, backed by `GraphEngine.run_cypher_graph`), dashboard-shaped Cypher helpers (`queries.py`), real git log/status (`git_info.py`), in-memory query telemetry for the dashboard's own Cypher console (`query_log.py`), database and memory readings plus their sampled history (`db_metrics.py`), a read-only view of MCP tool-call metadata recorded by the MCP server processes (`/api/mcp-telemetry`, read from the local store `devgraph/mcp/server.py` appends to — never through the MCP stdio server), SSE pub/sub (`events.py`: `EventBroadcaster`), and `static/index.html` (single hand-written file, no build step, Cytoscape.js from CDN). A second, independent read-only consumer of the same `GraphEngine`/`RepoRegistry` the tray owns — never routes through the MCP stdio server.
- `tests/` — mirrors the `devgraph/` package.
- `deploy/podman-compose.yml` — declarative alternative to the `podman run` setup command.
- `DEVGRAPH-CLIENT.md` — portable doc for another repo's coding assistant to connect to this DevGraph instance.
