# DevGraph

Local-first developer knowledge graph platform. Builds and maintains a structured architecture graph (Neo4j) of explicitly-registered repositories, exposed to coding assistants through an MCP layer — relationship/dependency/impact intelligence instead of plain semantic document retrieval. Full design intent lives in [Blueprints/Design Brief #1.md](Blueprints/Design%20Brief%20%231.md); read it before proposing architecture.

## Status

Phases 1-3 complete and verified: registry, graph engine, Tree-sitter Python indexer, container/API/datastore extractors, watcher, CLI, tray app (Phase 1); Requirements/DesignDecisions/ArchitectureNotes docs extractor (Phase 2); git history + opt-in PR/issue ingestion (Phase 3). 16 MCP tools total across the three phases, reachable over a real stdio transport (`devgraph/mcp/server.py`, built on `mcp.server.mcpserver.MCPServer`) — see [DEVGRAPH-CLIENT.md](DEVGRAPH-CLIENT.md) for how another repo's Claude Code instance connects to it and uses it day-to-day. Phase 4 (enterprise federation) is intentionally design-only/optional — see `Blueprints/Design Brief #2.md` — and should not be implemented without a fresh design pass informed by real multi-developer usage. Treat claims about specific extractors/tools as complete only once their code and tests actually land — check `devgraph/` before assuming a component works.

`devgraph add`/`rescan` now run a real full scan (`devgraph/indexer/dispatch.py`), and the watcher/tray app wire live changes through the same dispatcher, including file-delete cleanup (`GraphEngine.delete_nodes_by_source_file`) — this closed what was previously the biggest gap: extractors existed but nothing ever called them automatically.

**All previously-known gaps are now closed**, each verified end-to-end against RAG4 (a real ~1300-node repo in the parent folder — keep using it for realistic-scale testing; a synthetic fixture repo would not have caught most of these):

- **`CALLS` edge extraction** — the Python indexer now walks call expressions inside function/method bodies and emits `CALLS` edges (name-based, not type-resolved: `self.foo()`/`obj.foo()`/bare `foo()` all target the Function node named `foo`). `find_callers`/`impact_analysis` return real results (1207 edges on RAG4).
- **Module node keying changed from bare filename to full repo-relative path** (`services/api/main.py`, not `main.py`) — the real fix for multi-level relative imports and for two same-named files in different directories no longer colliding into one Module node. `index_file()` takes an optional `repo_root` to compute this; `dispatch.py` always passes it. Touches `git_history/extractor.py`'s `MODIFIES` target too (was bare filename, now the same repo-relative path).
- **Absolute dotted intra-repo imports now resolve** (`from services.api_gateway.clients import X` → also emits a `services/api_gateway/clients.py` target alongside the original bare-dotted-name target) — this is RAG4's actual import style (not dot-relative), and without this fix `IMPORTS` edges never resolved to any same-repo node at all, regardless of the Module-keying fix above.
- **Fixed a latent Tree-sitter Node-identity bug**: `child_by_field_name()` returns a fresh wrapper object per call, so `child is module_node` never matched — `from typing import List` was producing `imported_names=['typing', 'List']` instead of `['List']`. Fixed via byte-span comparison instead of object identity.
- **Service cross-linking**: the container extractor now captures each compose service's `build_context` (handles shorthand, long-form `context:`, and the context-is-repo-root-but-`dockerfile:`-points-into-a-subdirectory pattern). `dispatch.py`'s `_link_to_owning_service` matches a Python file's directory against the longest `build_context` prefix and links `Service -[:USES]-> Database/VectorStore/Queue` and `Endpoint -[:CALLS]-> Service` accordingly. `explain_architecture` now returns real `uses`/`calls` data (confirmed: `ingestion-service` → Qdrant/Neo4j, `api-gateway` → Neo4j, real endpoint→service links).

Git is initialized locally; no remote is configured yet. Container runtime is **Podman** (not Docker) — see the Design Brief and Implementation Plan.

## Commands

- Create venv: `python -m venv .venv`
- Install (editable, with dev deps): `.venv/Scripts/python -m pip install -e ".[dev]"`
- Run tests: `.venv/Scripts/python -m pytest`
- Start DevGraph's Neo4j (isolated container, not shared with other projects):
  `podman run -d --name devgraph-neo4j -p 127.0.0.1:7474:7474 -p 127.0.0.1:7687:7687 -e NEO4J_AUTH=neo4j/devgraph-local-dev -v devgraph_neo4j_data:/data -v devgraph_neo4j_logs:/logs docker.io/library/neo4j:5.26-community`
  (see `deploy/podman-compose.yml` for the declarative form; requires a compose provider to use directly — `podman run` above needs none)
- CLI entrypoint (once installed): `devgraph add <path>`, `devgraph list`, `devgraph status`

**Podman note**: on this machine `podman.exe` may not be on PATH by default even though it's installed — check `%LOCALAPPDATA%\Programs\Podman` before assuming it's missing. Never install new software to the host; DevGraph's dependencies live in `.venv/` and containers only. Never touch containers/volumes belonging to other projects (e.g. anything prefixed differently from `devgraph-`) — DevGraph's containers are named `devgraph-*` specifically to stay isolated from other services running on the same machine.

## Structure

- `Blueprints/` — numbered design docs for planned/completed work. `Design Brief #1.md` is the current source of truth for target architecture (principles, graph schema, MCP tool surface, roadmap phases). `Design Brief #2.md` is a deliberately unbuilt sketch of Phase 4 (optional, enterprise federation) — do not implement against it without a fresh design pass informed by real multi-developer usage. `Implementation Plan #2.md` is a build-ready handover plan (not yet implemented) covering rollout-readiness (bootstrap script, `devgraph doctor`/`client-config`, `add --full`) and extraction-quality fixes surfaced by live testing against RAG4 (docstring extraction into a new `description`/`docstring_full` property, a new `get_source` MCP tool, and a documented-but-unfixed `IMPORTS` resolution gap for `sys.path`-manipulated imports) — read it before picking up any of that work so decisions already made there aren't re-litigated. Check here before proposing new architecture; add new numbered briefs for major design changes rather than rewriting history in place.
- Root-level `CLAUDE.md` / `AGENTS.md` — working agreement and agent-facing instructions for this repo specifically.
- `devgraph/` — Phase 1 + Phase 2 + Phase 3 implementation:
  - `config/` — Pydantic settings, all security defaults off (telemetry, cloud sync, cross-repo, run_cypher).
  - `registry/` — SQLite-backed repo allowlist (`RepoRegistry`). The only source of truth for which paths may be watched/indexed. Also stores each repo's optional `docs_path` (Phase 2), `pr_source_enabled`/`issue_source_enabled` opt-in flags, and `last_indexed_commit` (Phase 3).
  - `graph/` — `GraphEngine` (Neo4j driver, idempotent MERGE upserts, schema constraints, `delete_nodes_by_source_file` for per-file cleanup on delete) and `schema.py` (canonical node labels / relationship types, including Phase 2's `Requirement`/`DesignDecision`/`ArchitectureNote`/`SATISFIES`/`DOCUMENTED_BY`/`DECIDED_BY`/`SUPERSEDES` and Phase 3's `Commit`/`PullRequest`/`Issue`/`MODIFIES`/`RESOLVES`/`REFERENCES` — import from here, don't hardcode label strings elsewhere). File-provenance property is inconsistent across extractors (`source_file` vs `file` vs `source`) — `delete_nodes_by_source_file` matches all three; unifying this onto one property name is unresolved follow-up work, not yet done.
  - `indexer/python/` — Tree-sitter-based Python extractor (`tree-sitter` + `tree-sitter-python`), per the Implementation Plan. Module nodes keyed by repo-relative path (pass `repo_root` to `index_file`). Extracts `CALLS` edges (name-based — no type resolution) alongside `CONTAINS`/`IMPORTS`/`EXTENDS`. `IMPORTS` targets: relative imports resolve to the sibling file's repo-relative path (`from . import x` -> `x.py` in the same dir, `from .sub.pkg import y` -> `sub/pkg.py`); dotted absolute imports emit both the bare dotted name AND a same-repo-file-path guess (`services.api.clients` -> also `services/api/clients.py`) so intra-repo absolute imports (the common real-world style) resolve too — a guess that doesn't match a real file simply never materializes an edge, same as any unresolvable import.
  - `indexer/containers/`, `indexer/apis/`, `indexer/datastores/` — Podman Compose, FastAPI/Flask/Django route, and datastore-client-usage extractors. `ContainerExtractor` also captures each compose service's `build_context` (source directory), used for Service cross-linking.
  - `indexer/dispatch.py` — routes changed/deleted files to the right extractor by name/extension (`index_paths`, `remove_paths`, `full_scan`). This is what `devgraph add`/`rescan`, the watcher's `on_changes` callback, and the tray app all now call — previously nothing did, so extractors existed but the graph never actually got populated automatically. Also runs `_link_to_owning_service` as a final pass per batch: matches each indexed Python file's directory against the longest `Service.build_context` prefix and links `Service -[:USES]-> Database/VectorStore/Queue` / `Endpoint -[:CALLS]-> Service`.
  - `indexer/docs/` — Phase 2 Markdown/front-matter extractor (`DocsExtractor`, `index_file`). Parses `type: requirement|design_decision|architecture_note` notes under a repo's configured `docs_path`; links via `links:`/`supersedes:`/`decided_by:` front-matter fields.
  - `indexer/git_history/` — Phase 3 `GitHistoryExtractor` (GitPython, purely local, no network) + `index_repo_history`. Incrementally walks commits newer than the registry's `last_indexed_commit`, creating `Commit` nodes and `MODIFIES` edges to `Module` nodes, keyed by the same repo-relative path as the Python indexer (git already reports changed-file paths this way — no bare-filename truncation).
  - `indexer/pr_issues/` — Phase 3's first external-network component. `PRIssueSource` protocol + `GitHubSource` implementation; `index_pr_issues` hard-gates on the repo's `pr_source_enabled`/`issue_source_enabled` registry flags (default off) — never wire this to run automatically.
  - `watcher/` — `WatcherManager`, registry-scoped-only file/git watching with debounce.
  - `mcp/` — the 16 high-level MCP tools (`tools.py`, including Phase 2's `explain_decision`/`find_requirements_for`/`trace_design_rationale` and Phase 3's `blame_component`/`find_related_prs`/`issue_history_for`) plus server wiring (`server.py`); `run_cypher` gated behind `enable_run_cypher` config.
  - `cli/` — Typer CLI (`devgraph add/remove/list/watch/rescan/status/annotate/index-history/pr-source/issue-source`). `annotate` sets a repo's `docs_path` and/or indexes a single note file; `index-history` walks git log incrementally; `pr-source`/`issue-source` flip the opt-in registry flags only (never make a network call themselves).
  - `agent/` — `TrayApp` (pystray), the thin shell wiring watcher + incremental indexing (via `indexer/dispatch.py`) + Neo4j health together. Does not host the MCP server — that's a separate stdio process an MCP client spawns itself (see `mcp/server.py`'s module docstring).
- `tests/` — mirrors `devgraph/` structure; 195 tests, run via `.venv/Scripts/python -m pytest`.
- `deploy/podman-compose.yml` — declarative form of DevGraph's isolated Neo4j container (needs a compose provider; `podman run` form in Commands above needs none).
- `DEVGRAPH-CLIENT.md` — a portable doc meant to be copied into (or summarized into) *another* repo's own `CLAUDE.md`/`AGENTS.md`, so a Claude Code instance working there knows how to register that repo with this DevGraph instance and use its MCP tools. Keep it in sync when the CLI/MCP surface changes — it duplicates just enough (paths, commands, tool list) to be self-contained for a reader who has never seen this repo before.

## Core design principles (from the Design Brief — hold these as constraints, not suggestions)

- **Explicit registration only.** Never inspect, scan, or index a path the developer hasn't explicitly mounted. No machine-wide or recursive discovery, ever — including from inside a tool call you're implementing.
- **Local-first.** No cloud dependencies, no telemetry by default, no external API calls from the platform itself.
- **Repository isolation.** Every graph object carries a `repo_id`; queries default to the current workspace's repo and never leak cross-repo results unless the developer opts in.
- **AI-optimized surface.** The MCP layer should expose high-level, purpose-built tools (e.g. `find_callers`, `impact_analysis`, `explain_architecture`) — Cypher is an advanced escape hatch, not the primary interface.

## Privacy

- **Never leave personal notes, data, or identifying items in any file in this repo.** No real names, no vendor/business names from personal documents, no personal local file paths (drive letters, `C:\Users\<name>\...`), no filenames from any personal document corpus. Use generic placeholders in examples (e.g. "the source repo path" instead of a real drive path). This holds even in a private repo — don't rely on repo visibility as the only safeguard.
- This matters especially here because the platform's own job is to index source trees and file paths — example paths, sample repo names, and mock graph data written into this repo should be fictional, not lifted from a real machine.
